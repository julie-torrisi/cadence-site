> 01 · The setup

Three layers, every prompt

I don't just chat with AI. Every prompt sits on three layers, and each one has a check so I can't fool myself.

1 · StandardsAlways on

My standing rules, loaded into every session in Claude, Claude Code and Cursor: real data, no made-up facts, no scope creep, and accessibility is not optional.

Check: would I put my name on it?
2 · SystemPer project

The design system, written so a model can follow it: tokens, components, voice, and every past mistake turned into a rule.

Check: does it pass the tests?
3 · BriefPer task

A short spec before the first prompt: the problem, the limits, and what done looks like.

Check: did it ship?

If two layers disagree, the brief wins. Hard rules always win.

The part that keeps it honest: after each session, a retro agent I built pulls out what went wrong and turns it into new rules. The system gets stricter without me remembering to make it stricter.

Steal my template+ 
# 1 · STANDARDS (always on)
- Use real components, real tokens and real data. No lorem ipsum.
- Never make up facts, numbers, quotes or sources. Say when you're unsure.
- Accessibility is not optional.
- Stay in scope. If the ask grows, stop and say so.
- Show me a plan before anything big. Ask before anything you can't undo.
- Done means shipped: a link, a file or a repo someone else can use.

# 2 · SYSTEM (per project, in the repo)
- CLAUDE.md / DESIGN.md: only these tokens and components. [paths]
- VOICE.md: how the brand talks, with good and bad examples.
- Rules a machine can check, plus tests that score the output.
- Lessons: every past mistake, written as a rule. My retro agent adds these after each session.

# 3 · BRIEF (per task)
Goal: [one sentence, and who it's for]
Done when: [how I'll know it worked]
Limits: [platforms, deadline, what not to touch]
Output: [exact format and where it goes]
Check: look at the real thing on a real device, not just the code.
Stop rule: 2 or 3 prompts with no progress = stop and fix the spec.

# IF THEY DISAGREE
Brief > System > Standards. Hard rules always win.

> 03 · Avoiding slop

Feeling fast isn't being fast

In a 2025 study, experienced developers said AI made them faster. A stopwatch said otherwise.

What they expected24% faster
What they felt20% faster
What happened19% slower

Source: METR trial, 16 developers, 246 real tasks, 2025

So I don't trust the feeling. I write the spec first, check the real thing on a real device, and if two or three prompts don't get me closer, I stop and fix the spec instead of rewording.

> 04 · Proof

Did it ship?

That's the main metric, along with how many rounds it took and whether it held up. If you can't click it, it doesn't count.
